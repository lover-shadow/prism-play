## 第一部分：体系架构与业务规格书 (SPEC)

### 1.1 核心问题定义与架构演进定位
在流媒体聚合系统建设中，传统的“全量静态镜像存储”面临三大物理死结：
1. **内容时效性死结**：短剧影视每日上新，全量静态镜像导致本地库沦为“死水”，新剧无法自然出现；
2. **资源与死链死结**：3.5 万部全量分集（150万~200万行）一次性硬塞会打爆 D1 单日 10 万行免费配额，且随时间推移沉淀大量僵尸死链；
3. **人工维护死结**：依赖人类或 Agent 在本地手动运行脚本，违背 Serverless 无人值守的核心宗旨。

**本体系定位**：建立**“精选高热基准底座 + 全网即搜即入 JIT 穿透 + 云端定时增量自生”**的工业级动态内容中枢。

### 1.2 机制一：防封并发与滑动队列采集规格 (Anti-Ban Ingest SPEC)

为防止大批量抓取时触发上游 Nginx / CDN 的 429（Too Many Requests）或 IP 封禁，采集引擎必须严格遵守以下物理限制：

1. **滑动窗口并发约束**：
   - 最大并发请求数严格锁死为 **3**（`concurrency = 3`），严禁发起无序高并发；
   - 每次请求发起后，强制插入 **200ms ~ 300ms** 的生理抖动延迟（Jitter）；
2. **断点持久化与快照存档 (Checkpointing)**：
   - 每次网络抓取成功的一页原始 JSON，立即写入本地 `cache/raw_pages/ch_{channel}_pg_{page}.json`；
   - 采集引擎启动前优先扫描缓存目录，若已存在且未过期则直接读取本地快照，**绝不向上游重复发起相同请求**；
3. **退避自愈算法 (Exponential Backoff)**：
   - 遇 HTTP 429 / 503 或网络超时，按照 `1s -> 2s -> 4s` 梯次退避重试，最大重试次数为 3 次；连续失败 3 次记录错误墓碑并跳过该页，保证整体批次不被阻塞挂起。

### 1.3 机制二：多源合并与跨源择优容灾规格 (Multi-Source Merge SPEC)

同时接入魔都短剧 (`modu`)、河马剧场 (`hema`)、火龙漫剧 (`huolong`) 等成熟站源时，实行两级归并：

1. **剧目主表 (`content_items`) 归并原则**：
   - 对齐键：`规范化中文剧名` + `所属一级频道`；
   - 冲突裁决：
     - 若同名剧在多源存在，保留分集数更多（`episode_count` 更大）、封面图分辨率更高（带官方 CDN 优先）、简介更完整的源作为主实体；
     - 剧目 ID 保持确定性散列或规范命名，避免重复建档。
2. **分集多源热备 (`episode_sources`) 关联原则**：
   - 分集主表 `content_episodes` 记录统一的自然集数（第 1 集、第 2 集……）；
   - 播放源表 `episode_sources` 以 `(episode_id, provider_id)` 联合主键并存登记各源真实播放链接；
   - 服务端路由 `/api/episodes/:id/playback` 执行动态择优：
     - 读取 `source_providers` 中登记的节点优先级 `priority` 与探针延迟 `latency_ms`；
     - 自动挑选最优源签发受控代理句柄；若主力源返回 4xx/5xx，系统自动降级切换至备用源。

### 1.4 机制三：成人内容（个人探索）四重物理绝缘规格 (Private Isolation SPEC)

作为项目的 **P0 级法律合规硬红线**，成人内容（个人探索 / private）必须实行全链路彻底隔离：

1. **管道物理隔离**：
   - 标准公开内容生成 `seed-public-baseline.sql`；
   - 成人私密源走独立沙箱管道，单独生成受保护的 `seed-private.sql`，两类数据在构建期零交叉。
2. **数据库引擎级强等式 CHECK 约束**：
   - 必须通过 D1 底层 CHECK 强制焊死：
     ```sql
     CHECK((channel_id = 'private' AND is_private = 1 AND shareable = 0) OR (channel_id <> 'private' AND is_private = 0))
     ```
   - 凡私密作品：`channel_id` 恒为 `'private'`，`is_private` 恒为 `1`，`shareable` 恒为 `0`；引擎底层物理阻断越权写入。
3. **全文检索与变更日志物理剔除**：
   - **`public_search_fts` 绝对禁止录入**：公共全文索引中严禁包含任何 `is_private = 1` 的词元，公网搜索完全查无此内容；
   - **`public_catalog_changes` 绝对禁止录入**：公开增量日志表不记录私密作品，防止外部通过版本差量反向嗅探私密片单。
4. **服务端双重准入防护 (Double Admission)**：
   - 必须同时具备：① 经 Ed25519 验签的有效高级卡（B/Y/S）JWT 令牌；② 用户在免责二次确认后由边缘颁发的有效 `X-Private-Session` 短时凭据（纯内存，冷启即焚）；
   - 任一条件缺失，接口返回的 HTTP 响应体、状态码（404）及处理耗时与“资源不存在”完全相同，严防基于状态码的侧信道枚举。

### 1.5 机制四：全网 3.5 万+ JIT 穿透搜索与即时沉淀规格 (JIT Ingest SPEC)

用于彻底消除“冷门长尾剧搜不到”的短板：

1. **搜索双模流水线 (`GET /api/search`)**：
   - **Step 1 (本地秒出)**：优先检索 D1 本地 `public_search_fts`，命中条目直接高亮返回（耗时 ~0.2ms）；
   - **Step 2 (穿透兜底)**：若 D1 结果不足或未完全匹配，边缘自动发起对成熟站源的穿透检索接口（如 `moduapi?ac=detail&wd={keyword}`）；
   - **Step 3 (轻量清洗与输出)**：将上游搜索结果通过“双字题材规则引擎”清洗为标准 JSON 格式，与本地结果融合返回给客户端；
   - **原则**：**搜索阶段“只查不存”**，不向 D1 发起任何写操作，防止恶意刷词导致数据库垃圾膨胀。
2. **点击播放即时沉淀 (Just-In-Time Lazy Persist)**：
   - 当用户在客户端点击穿透搜索出来的某部剧进入详情或起播时（请求 `GET /api/titles/:id` 或 `/api/episodes/:id/playback`）：
   - 边缘检测到该 ID 为穿透引入且 D1 不存在时，自动在同一后台事务中：
     ① 提取剧目主信息写入 `content_items`（归入 21 主流双字分类）；  
     ② 提取分集与播放流写入 `content_episodes` 与 `episode_sources`；  
     ③ 自动将其 Origin 登记入 `source_providers` 白名单；  
     ④ 签发正常受控代理流媒体句柄。  
   - **效果**：被真实用户看过的剧自动沉淀为本地永久资产，越用越丰富，且永远不占无用配额。

### 1.6 机制五：技术暗礁防御规格 (Defensive Architecture SPEC)

1. **搜索空值负缓存 (Negative Cache)**：
   - 针对完全搜不到的无意义乱码词（如 `xyz123abc`），在 Cloudflare Workers 内存中维持 LRU 负缓存（TTL: 5分钟），相同乱码词短时间内不重复穿透上游。
2. **上游请求超时硬熔断**：
   - 所有边缘发往外部成熟源的网络请求，强制绑定 `AbortSignal.timeout(1500)`（1.5 秒硬超时）；
   - 超时立即中断并优雅降级为仅呈现本地结果，**绝对禁止因为外部网络卡顿导致客户端死等转圈**。
3. **封面图同源安全 HTTPS 强制转接**：
   - 外部来源的封面地址无论协议为 `http://` 还是 `https://`，客户端一律消费 `https://play.prismos.org/proxy/img/:id`；
   - 边缘负责通过 HTTPS 安全代理输出，并强加 `Cache-Control: public, max-age=300` 与 ETag 重协商，彻底规避 Android 原生 WebView 的混合协议阻断（Mixed Content）风险。

## 第二部分：工程实施行动计划 (Action Plan)

### 阶段一：批量稳态采集引擎与万部级本地构建 (Phase 1)
- **目标**：在本地建立受控、抗限流的批量抓取与清洗引擎，构建约 **2,000 部** 高热公开精品基准大库（短剧 1,000 部、电影 400 部、动漫 350 部、纪录片 250 部），充分利用今日剩余的 95,000 行 D1 写入配额。
- **具体工序**：
  1. 升级 `edge/scripts/seed-runner.mjs`，引入并发度为 3 的滑动窗口与 200ms Jitter 延迟机制；
  2. 实现同名剧去重与多源择优逻辑；
  3. 执行 21 个主流双字分类（战神/逆袭/都市/科幻等）严格归一化清洗；
  4. 分集采用轻量核心集写入（每部保留精选核心集，压减单部物理写入行数至 4~5 行）；
  5. 输出标准批次文件 `edge/scripts/seed-public-baseline.sql`。

### 阶段二：R2 暂存中转与 D1 一键整库灌装 (Phase 2)
- **目标**：利用 Wrangler 官方管道，将生成的基准大库一次性完整推送到云端 D1。
- **具体工序**：
  1. 执行 `npx wrangler d1 execute prism-play-db --remote --file=scripts/seed-public-baseline.sql`；
  2. 观察控制台，确认 Wrangler 将 SQL 文件打包上传至 Cloudflare 临时 R2 存储桶，并在 D1 服务端自上而下一次性批量执行导入；
  3. 验证写入行数（约 10,000~15,000 行，稳在每日 10 万行配额安全线内）；
  4. 执行 D1 统计核验，确认四大频道片单规模达到 2,000 部级别；
  5. 手机真机冷启动刷新验证，检查分类胶囊与海报瀑布流饱满度。

### 阶段三：边缘 Workers JIT 穿透搜索与即时沉淀部署 (Phase 3)
- **目标**：升级 `edge/src/routes/search.ts` 与详情/播放路由，打通全网 3.5 万+ 海量穿透。
- **具体工序**：
  1. 在 `edge/src/routes/search.ts` 中接入异步上游穿透逻辑，绑定 1.5 秒硬超时熔断与空值负缓存；
  2. 在 `edge/src/routes/titles.ts` 与 `playback.ts` 中实现 JIT 惰性入库逻辑（点击播放时原子写入 `content_items`、`content_episodes`、`source_providers`）；
  3. 执行自动化测试套件与契约门禁复核，确保 100% 保持绿色全通；
  4. 执行 `npx wrangler deploy` 发布新版边缘代码至生产环境；
  5. 真机实测搜索库外冷门剧，验证即搜即看与自动沉淀机制。

### 阶段四：GitHub Actions 无人值守增量定时追新流水线 (Phase 4)
- **目标**：彻底摆脱人工开机运行脚本，实现云端每日自动生长。
- **具体工序**：
  1. 编写 `.github/workflows/content-sync.yml`；
  2. 配置 Cron 定时调度（例如每日北京时间凌晨 03:00 自动触发一次）；
  3. 工作流自动拉取成熟源当天最新上架的 50~100 部热门新作；
  4. 自动清洗分类、分词、写入 D1 并签发自增目录版本号；
  5. 将运行状态自动记入 CI 日志与监控通知。

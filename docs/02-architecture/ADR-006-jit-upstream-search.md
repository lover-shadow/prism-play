## 背景与问题陈述 (Context and Problem Statement)

《光影Play》现有架构建立在一条不可动摇的前提上。`edge/src/index.ts:109-113` 的原文声明为：

> "Ingestion is adapter-injection only: **the Worker performs no upstream call and knows no URL**, so the registry stays empty until Stage 2 registers an authorized source adapter."

这条前提支撑着三个既有的合规与安全保证：

1. **上游身份零暴露**（`AGENTS.md` 二·1「彻底去平台化」）：Worker 不持有上游域名，因此任何响应体、错误信息或日志中都不可能泄漏上游站源名；
2. **SSRF 防护的唯一入口**：所有出网都经 `edge/src/media/upstream.ts` 的 `assertAllowedTarget()` + D1 `source_providers` 白名单，且强制 `redirect: 'manual'` 逐跳复核；
3. **客户端零硬编码源**（`ADR-003`）：客户端启动时向 `/api/channels` 与 `/api/sources` 获取动态脱敏配置，上游变更由云端空中调度，客户端无需发版。

**历史矛盾**：原设计只在本地 FTS5 零命中后穿透并在点击起播时入库；此口径已由 2026-10-06 决策替代。覆盖数量是旧方案估算，不是当前已核实来源规模。

**已采纳边界**：允许 Worker 在受控配置中持有上游地址并进行真实搜索，但绝不允许用户指定任意目标；白名单、逐跳 SSRF 校验、限流和响应/日志脱敏必须保留。原“Worker 不知道 URL”只描述历史实现，不能再作为零暴露的证明；应以真实响应、日志与出网防护测试举证。

## 关键风险量化

| 风险 | 机理 | 影响 |
| :--- | :--- | :--- |
| **免鉴权出网代理** | openapi 中 `/api/search` 声明为**免认证**。任何人可无门槛调用，触发边缘对外发起一次真实网络请求 | 被刷量时消耗我们的 Workers 请求配额与 CPU 预算，可能连带影响付费用户的核心链路 |
| **配额击穿** | 无限流时，单机可高频构造不同关键字穿透 | Workers 请求配额耗尽 → 全站接口不可用 |
| **去平台化取证失效** | Worker 首次持有上游域名，日志与异常堆栈可能带出源名 | 违反 `AGENTS.md` 二·1，破坏「零外部品牌名暴露」的可举证性 |
| **SSRF 旁路** | 若穿透实现不复用既有白名单校验 | 绕过 `assertAllowedTarget()` 的三跳限制与保留 IP 拒绝，形成新的攻击面 |
| **响应不可控** | 上游返回内容的质量、时延与可用性完全不在我们控制内 | 上游抖动直接转化为用户端搜索卡顿 |

## 备选方案 (Considered Options)

### 方案 A：维持现状，不做边缘穿透（**保底方案**）
- 仅依赖 D1 本地 FTS5（现有 8,874 部）。
- **优点**：零新增风险，完全保持现有架构前提与全部合规边界；无额外配额消耗。
- **缺点**：库里没有的剧搜不到（长尾覆盖为零）。
- **结论**：**这是当前唯一完全无风险的选择。** 若长尾需求可通过扩大基准库规模（本地受控入库）解决，则不必引入边缘出网。

### 方案 B：边缘穿透 + 全量防护（原设计 + 补齐防护）
- `/api/search` 保持免认证，但增加：按 IP 独立限流、5 分钟空值负缓存、1.5s 硬超时熔断；出网强制复用 `assertAllowedTarget()` 与 `source_providers` 白名单。
- **优点**：长尾覆盖完整；可复用既有 SSRF 防护设施。
- **缺点**：仍需接受「Worker 持有上游域名」这一既成事实，去平台化的可举证性下降（虽可通过日志脱敏缓解，但无法回到「Worker 根本不知道 URL」的强姿态）；免认证端点仍是对外开放面。
- **决策**：2026-10-06 已接受受控上游访问；旧方案的零命中触发、仅起播入库和固定负缓存描述由下文强制条款替代。

### 方案 C：穿透能力移出边缘，走构建期/批处理通道（**架构最一致**）
- 边缘**永远不出网**。长尾覆盖改由 `GitHub Actions` / 本地批处理按需沉淀：
  - 定期任务扫描高频未命中关键字（可从搜索日志或手工清单得到），批量抓取后写入 D1；
  - 或由用户侧「未找到？提交补全」轻量入口触发异步入库队列。
- **优点**：100% 保留现有架构前提；边缘零出网、零新攻击面；与模块四（Actions 定时追新）复用同一条通道，工程上更统一。
- **缺点**：长尾响应不是"即时"的，需等待下一个批处理周期；覆盖速度慢于即时穿透。
- **结论**：与现有架构最自洽的方案，且不需要推翻任何既有声明。

### 方案 D：穿透能力放在客户端（不推荐）
- 由 APP 直连上游。
- **否决理由**：直接违反 `ADR-003`「客户端零硬编码上游地址」的根本决策，且把上游身份暴露给客户端可被反编译提取。**不建议列为候选。**

## 已采纳决策（2026-10-06）

采用方案 B 的受控真实来源搜索，结合静态全量基底 + 共享发现增量；不每搜重写整个 manifest。App 提交查询后先显示本机结果，默认自动联网补充，无论本机是否命中；不要求零命中或手点才能启动。按作品身份去重合并，搜索结果纵向三列且全部可达，分页/加载更多不能截断在首批。

关键词查询缓存与共享永久剧库是不同对象：查询缓存只在新鲜核验有效期内复用；公开作品核验成功后共享持久保存，不因关键词 TTL 到期删除。过期结果必须重新核验当前公开身份、完整集表和可用线路后才作为新鲜联网结果返回；失效作品不因已入库而永久可播。

## 方案 B 的强制实现约束

1. **白名单唯一入口**：穿透出网必须经 `listAllowedUpstreamOrigins()` + `assertAllowedTarget()` 或经同等审计的受控配置入口，保留保留 IP 拒绝与 `redirect: 'manual'` 逐跳复核；禁止用户传入 URL 或旁路直连。不可因旧 D1 表停用而移除白名单防护。
2. **限流与并发合并**：按 `CF-Connecting-IP` 独立限流，窗口、上限、超时及缓存 TTL 为具名配置。查询缓存与同词在途请求合并的键包含规范化查询、频道/标签等过滤条件、public 边界及来源配置版本；翻页不串结果。跨请求共享能力的实际范围须验证，不把单实例内存去重宣称全局合并。
3. **真实核验与持久化**：对配置中的公开来源执行真实搜索；先核验 public 身份、可信作品映射、完整集数/季数与真实可用线路，再幂等共享保存作品 facts 和发现索引。禁止同名即合并、空线路冒充可播、只返回两集或等点击起播才保存。详情、海报、分享与搜索必须读取同一可见事实，不能用旧公开 D1 兜底掩盖事实损坏。
4. **两类缓存与更新**：正缓存只复用新鲜核验结果；已入共享库仍须追新集/新季、重验线路与撤片状态。真正完成搜索且确认无结果才写短暂负缓存（上限 5 分钟，可更短）；超时、限流、来源失败或核验失败不当作无结果，不写成功空集负缓存。已有本机结果可保留并提示联网补充失败/重试，不能声称搜遍无结果。
5. **隔离与脱敏**：private/exclude 不进入公开查询、缓存、共享增量、日志或客户端持久层，私密双准入不变。响应公开元数据、错误与日志零外部品牌名；日志不记录上游域名、原始 URL/响应或异常堆栈。已批准 `lines[].mediaUrl` 仅为播放清单运行时受控例外，不扩展至目录/搜索/日志。用真实响应及日志断言验证，不以抽象 Provider 编号代替脱敏证明。
6. **基底与发现增量**：静态全量基底沿用同 generation 校验和 blobs 先、manifest 后发布；发现以独立共享持久增量提交，不每次搜索刷新全量 manifest。客户端按稳定作品 ID/版本幂等合并，数据与同步进度原子提交；重启、整包更新及同步失败保留已发现作品，仅明确撤片/删除事实可移除。发现同步采用 `GET /api/search/discoveries?after=&limit=`，after为独立seq cursor（初始0），limit默认60/max100，返回changes[{seq,workId,operation:upsert|withdraw,updatedAt,card?}],cursor,hasMore（Unix秒、可选公开ContentItem）；非catalog revision，无私密元数据/墓碑。D1存metadata/任务，R2存事实/cursor，独立DISCOVERY_BUCKET无r2.dev；0005发现五表、0006 jobqueries/jobs两表，总业务37表（不含FTS影子表）。当前基线disabled/private不可被发现覆盖；永久metadata与播放事实24小时刷新分离，查询TTL不删metadata。
7. **交互与兼容**：搜索三列纵向网格，加载更多覆盖全部去重结果；显示准确已展示/已加载数量，只有已知完整总数才能称总数，明确本机/联网补充、离线/过期/失败与真实匹配标签。`GET /api/search` 保留可选hasMore、items/page与pageSize≤20，增可选discoveryPage（1～200），响应discoveryPending/discoveryFailed/retryAfterSeconds；App按等待秒数自动同词同页poll到pending结束，切词取消旧poll及迟到响应。成功partial保留已有结果，不伪装成功empty；缺hasMore不是false或无更多的证明。本轮仅同步文档，verify_contracts由主会话更新。
8. **门禁与发布**：用户已允许必要云端施工、CI 与独立验收 APK；正式官网 APK/OTA 仅验收后发布。本次不执行源码、云、CI、构建、权限或 Git 操作；G0 静态门禁与 G1～G4 真实搜索、并发、持久同步和真机证据分别验收，Accepted 不代表已部署或已验收。

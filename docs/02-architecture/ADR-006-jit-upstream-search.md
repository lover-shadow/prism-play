## 背景与问题陈述 (Context and Problem Statement)

《光影Play》现有架构建立在一条不可动摇的前提上。`edge/src/index.ts:109-113` 的原文声明为：

> "Ingestion is adapter-injection only: **the Worker performs no upstream call and knows no URL**, so the registry stays empty until Stage 2 registers an authorized source adapter."

这条前提支撑着三个既有的合规与安全保证：

1. **上游身份零暴露**（`AGENTS.md` 二·1「彻底去平台化」）：Worker 不持有上游域名，因此任何响应体、错误信息或日志中都不可能泄漏上游站源名；
2. **SSRF 防护的唯一入口**：所有出网都经 `edge/src/media/upstream.ts` 的 `assertAllowedTarget()` + D1 `source_providers` 白名单，且强制 `redirect: 'manual'` 逐跳复核；
3. **客户端零硬编码源**（`ADR-003`）：客户端启动时向 `/api/channels` 与 `/api/sources` 获取动态脱敏配置，上游变更由云端空中调度，客户端无需发版。

**当前矛盾**：为覆盖全网约 3.5 万部长尾内容（避免全量静态镜像），原设计提出让 `/api/search` 在本地 FTS5 未命中时，由边缘**异步直连外部成熟源检索接口**（如 `...?ac=detail&wd={keyword}`）并把结果清洗后返回客户端；用户点击起播时再惰性沉淀入库。

这与上述第 1、2 条前提正面冲突：一旦 Worker 掌握上游 URL 并对外发起任意关键字的网络请求，`/api/search` 就会变成一个**免鉴权的开放出网代理**。

---

## 关键风险量化

| 风险 | 机理 | 影响 |
| :--- | :--- | :--- |
| **免鉴权出网代理** | openapi 中 `/api/search` 声明为**免认证**。任何人可无门槛调用，触发边缘对外发起一次真实网络请求 | 被刷量时消耗我们的 Workers 请求配额与 CPU 预算，可能连带影响付费用户的核心链路 |
| **配额击穿** | 无限流时，单机可高频构造不同关键字穿透 | Workers 请求配额耗尽 → 全站接口不可用 |
| **去平台化取证失效** | Worker 首次持有上游域名，日志与异常堆栈可能带出源名 | 违反 `AGENTS.md` 二·1，破坏「零外部品牌名暴露」的可举证性 |
| **SSRF 旁路** | 若穿透实现不复用既有白名单校验 | 绕过 `assertAllowedTarget()` 的三跳限制与保留 IP 拒绝，形成新的攻击面 |
| **响应不可控** | 上游返回内容的质量、时延与可用性完全不在我们控制内 | 上游抖动直接转化为用户端搜索卡顿 |

## 备选方案 (Considered Options)

### 方案 A：维持现状，不做边缘穿透（**保底方案**）
- 仅依赖 D1 本地 FTS5（现有 8,874 部）。
- **优点**：零新增风险，完全保持现有架构前提与全部合规边界；无额外配额消耗。
- **缺点**：库里没有的剧搜不到（长尾覆盖为零）。
- **结论**：**这是当前唯一完全无风险的选择。** 若长尾需求可通过扩大基准库规模（本地受控入库）解决，则不必引入边缘出网。

### 方案 B：边缘穿透 + 全量防护（原设计 + 补齐防护）
- `/api/search` 保持免认证，但增加：按 IP 独立限流、5 分钟空值负缓存、1.5s 硬超时熔断；出网强制复用 `assertAllowedTarget()` 与 `source_providers` 白名单。
- **优点**：长尾覆盖完整；可复用既有 SSRF 防护设施。
- **缺点**：仍需接受「Worker 持有上游域名」这一既成事实，去平台化的可举证性下降（虽可通过日志脱敏缓解，但无法回到「Worker 根本不知道 URL」的强姿态）；免认证端点仍是对外开放面。
- **待决项**：是否接受该姿态变更。

### 方案 C：穿透能力移出边缘，走构建期/批处理通道（**架构最一致**）
- 边缘**永远不出网**。长尾覆盖改由 `GitHub Actions` / 本地批处理按需沉淀：
  - 定期任务扫描高频未命中关键字（可从搜索日志或手工清单得到），批量抓取后写入 D1；
  - 或由用户侧「未找到？提交补全」轻量入口触发异步入库队列。
- **优点**：100% 保留现有架构前提；边缘零出网、零新攻击面；与模块四（Actions 定时追新）复用同一条通道，工程上更统一。
- **缺点**：长尾响应不是"即时"的，需等待下一个批处理周期；覆盖速度慢于即时穿透。
- **结论**：与现有架构最自洽的方案，且不需要推翻任何既有声明。

### 方案 D：穿透能力放在客户端（不推荐）
- 由 APP 直连上游。
- **否决理由**：直接违反 `ADR-003`「客户端零硬编码上游地址」的根本决策，且把上游身份暴露给客户端可被反编译提取。**不建议列为候选。**

---

## 待 Master 裁决的核心问题

**是否允许 Cloudflare Worker 持有上游域名并对外发起搜索性网络请求？**

- 若**不允许** → 采方案 A 或 C，模块三降级为「构建期按需沉淀」，本 ADR 记录为 Accepted（方案 C）；
- 若**允许** → 采方案 B，并在本 ADR 中明确写入以下强制条款：出网必须复用 `assertAllowedTarget()`、必须限流、必须脱敏日志、负缓存上限、以及"上游站源名永不进入响应体与日志"的可验证口径。

---

## 若采方案 B，必须固化的实现约束

1. **白名单唯一入口**：穿透出网必须经 `listAllowedUpstreamOrigins()` + `assertAllowedTarget()`，禁止任何形式的旁路直连；
2. **限流**：按 `CF-Connecting-IP` 独立计数（复用 `edge/src/core/rate-limit.ts`），窗口与上限须在 `edge/src/core/constants.ts` 登记为具名常量（禁止散落魔法数字）；
3. **熔断**：`AbortSignal.timeout(1500)` 硬超时，超时即降级为仅返回本地结果；
4. **负缓存**：未命中的查询词在 Worker 内存做 5 分钟 LRU 负缓存，防止乱码词反复穿透；
5. **脱敏**：响应体、错误信息、`console` 日志三者均不得出现上游域名或站源名；须有自动化测试断言响应体不含上游 Origin 字符串；
6. **不写入**：搜索路径**只查不存**，D1 写入只发生在用户点击起播的惰性沉淀路径上。

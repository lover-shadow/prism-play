# 双 Agent 协同监理模式与工程治理方法论 (DUAL-AGENT-COLLABORATION-METHODOLOGY.md)

> **生效日期**：2026-10-02  
> **适用范围**：跨项目通用复杂全栈研发与多 Agent 编排  
> **编制背景**：在《光影Play》(Prism Play) 2.0 从文档规范收敛到端到端 Android 真机上线的工程战役中，团队实践了“施工总包 (Chief Builder) + 项目监理 (Audit Director)”的双 Agent 协同机制，取得了 29,339 行代码无污染交付、672 项测试全绿、真机一次性跑通的重大战果。特将该模式提炼为标准化方法论，供后续复杂任务复用。

---

## 一、 为什么单 Agent 应对复杂工程必然退化？

1. **上下文遗忘与注意力漂移 (Context Degradation)**：
   长对话一旦跨越 10~20 轮，模型对早期细节（如安全 CHECK 约束、接口命名、Tokens 规范）的敏感度呈断崖式下跌，极易出现“前改后漏、自相矛盾”；
2. **“既当运动员又当裁判员”的自恋陷阱 (Verification Bias)**：
   自己编写代码的 Agent，往往会写出自证通过的伪单元测试，对潜伏的空指针、类型隐式转换或跨域安全拦截视而不见；
3. **权限与安全隔离需求 (Permissions Boundary)**：
   应用层代码施工并不需要直接暴露 Cloudflare / AWS 生产环境变量或主域 DNS 解析权限。

## 二、 双 Agent（总包 + 监理）的核心分工铁律

```
┌──────────────────────────────────────────────┐          阶段产物 / 门禁申请          ┌──────────────────────────────────────────────┐
│        施工总包 Agent (Chief Builder)        │ ────────────────────────────────────> │        项目监理 Agent (Audit Director)       │
│                                              │                                      │                                              │
│ • 职责：全权负责应用业务逻辑与测试实现      │                                      │ • 职责：架构把关、基础设施拨备与门禁裁决     │
│ • 权限：本地源码读写、单元测试实跑          │ <──────────────────────────────────── │ • 权限：Cloudflare/云端操作、CI流水线维护    │
│ • 纪律：Inside-Out 演进、TDD 驱动、单文件≤300行 │          门禁通过公文 / 外部资源供给         │ • 纪律：客观验证绝不放水、主动正本化白皮书   │
└──────────────────────────────────────────────┘                                      └──────────────────────────────────────────────┘
```

### 1. 施工总包 Agent (Chief Builder) 的行为准则
- **专职边界**：沉下心搞代码与测试，不分心做外部基础设施配置；
- **Inside-Out 演进**：先写核心数据模型与存储域，再做网络适配，最后装配 UI，绝不倒置；
- **结构化汇报机制**：拒绝口水话与代码堆砌，每次阶段停下必须交付：
  - 交付文件数与物理代码行数 (LOC)；
  - 终端实际跑通测试的命令输出证据；
  - 遗留问题与已知限制清单（诚实报告不可在当前环境证明的硬件项）。

### 2. 项目监理 Agent (Audit Director) 的行为准则
- **客观公理裁决**：只认自动化测试脚本、AAPT2 与真实 CI 运行日志，不接受“应该没问题”的虚假保证；
- **外部关键资源专职供给**：
  - 云端 D1 数据库、KV 缓存、R2 桶创建与物理迁移；
  - 生产 Ed25519 公私钥对生成与配对供给；
  - GitHub Actions 自动化编译流水线配置与故障修复；
- **正式公文准入准出 (Gate G0 ~ G4)**：
  - 每个阶段结束，监理必须签发具有法律效力的审查裁决书（如 `G1-SUPERVISION-DECISION-*.md`），明确放行条件与下一个阶段的施工指令。

## 三、 五级刚性阶段门禁机制 (Gate Lifecycle)

| 阶段门禁 | 门禁名称 | 强制准出硬指标 | 监理裁决输出 |
| :--- | :--- | :--- | :--- |
| **Gate G0** | **施工前契约终审** | OpenAPI、D1 Schema、PRD、SPEC、Tokens 逐字对齐，`verify_contracts.py` 全绿 | 施工总包指令包 (`BUILDER-DISPATCH-PACKAGE.md`) |
| **Gate G1** | **云端事实与核心引擎** | D1 物理迁移完成，原子核销、状态机与双分支用例 100% 通过 | G1 通过决定书 + 阶段 2 施工授权 |
| **Gate G2** | **传输同步与受控代理** | 18 个合规端点全部挂载，受控媒体代理与 HLS 重写通过，分享/下载 H5 就绪 | G2 通过决定书 + 阶段 3 施工授权 |
| **Gate G3** | **客户端视界与播放宿主** | 四大存储域物理隔离落地，ArtPlayer 全手势与锁屏保活通过，前端构建 0 错误 | G3 通过决定书 + 生产公钥注入指令 |
| **Gate G4** | **全链路回归与出厂装配** | 18/18 项 AC 矩阵全署名覆盖，CI 云端流水线全绿，`app-debug.apk` 真机跑通 | G4 终审裁决书 + 出厂交付安装包 |

## 四、 伴生交付与元规则沉淀

任何多 Agent 协同体系在任务收口时，必须自发完成：
1. **白皮书伴生交付**：把隐藏在终端、云端环境变量和构建配置中的非自解释工程事实（如 CORS 机制、DNS 代理、SSH 跳板）整理成独立的架构正本；
2. **元规则抽象**：提炼普遍适用的工程规律并写入全局记忆，严禁将项目特定名词伪造成通用规则。

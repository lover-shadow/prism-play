## 三、 M-3：云端开关的工程落点与一个新的高危旋钮

现行 D1 约束把私密频道的准入档位**焊死**了：`CHECK((id <> 'private' AND requires_tier = '0') OR (id = 'private' AND requires_tier = 'ADVANCED'))`（`sql:84`）。要做成"云端可改"，需改为：

1. `channels.requires_tier` 允许存受控档位集合（如 `'Q'`、`'B,Y,S'`、`'ALL_PAID'`），并保留"仅 `id='private'` 可非 `'0'`"这条防误配约束；
2. **第二条件不动**：当次手动开启（`X-Private-Session`）仍是硬前置，不因云端开关而放松——这是 AC-02 双层隐形的核心，不可被这个旋钮间接关掉；
3. `openapi.yaml` 的 `ChannelItem.requiresTier.items` 由 `enum [B,Y,S]` 放宽为与档位全集一致；
4. `AC-02` 第 1 条"仅有效 B/Y/S 授权后才在设置露出开关"改写为"仅当设备当前档位命中云端下发的 `private.requiresTier` 集合时露出"。

**必须提示的后果**：这个旋钮一旦允许把 `Q` 加进集合，就等于"¥9.9 即可进入敏感内容入口"，是本项选择里风险最高的一种组合（我在选项说明里已标注）。因此建议同时补一条最小治理：**该字段每次变更须在服务端留审计记录**（谁改的、改成什么、何时），避免出现"运营手滑把 9.9 全量放开"且无人可追责的局面。这一条属工程可自决，无需 Master 再裁决，但需要写进 SPEC 才算数。

## 四、 M-4：双分支奖励需要新增字段，并解决与卡密时长的冲突

现契约里 `invitation_logs.reward_days INTEGER DEFAULT 3` 是单一数值，无法表达两种奖励性质。落点：

1. `invitation_logs` 增加 `reward_type TEXT NOT NULL CHECK(reward_type IN ('NUDGE_FREE','TIER_EXTEND'))`；
2. `NUDGE_FREE` → 累加 `devices.exempt_until`（此字段目前**除本文件外全库仅存在于 SQL**，本轮裁决后它第一次获得正式语义与写入方，R-6 由此关闭）；
3. `TIER_EXTEND` → 延长 `devices.expires_at`；
4. **必须一并定义的冲突**：会员的 `expires_at` 原本由卡密 `duration_days` 决定。邀请奖励延长它之后，`card_coupons` 台账与设备实际有效期会不一致。建议明确规则："邀请奖励产生的增量记入 `devices.expires_at`，不回写卡密，且卡密被吊销时该增量保留"——否则 AC-14 的吊销分支会把免费赚来的天数一起收走，是客诉点；
5. **仍待 Master 确认的次级口径（本 Agent 给默认值，无异议即按默认施工）**："会员"指 tier ∈ {Q, A, B, Y, S} 且未过期；"非会员"指 tier = '0' 试用态。

## 五、 M-8：允许备份带来一个必须做的排除项，否则换机反而坏

"允许观看历史进系统备份"不能简单打开 `allowBackup`，因为 **Android 的自动备份是整库级别的**，会连带备份：

- JWT 授权凭证（`PRD:272` 要求存于 Android Keystore 支持的加密存储）。Keystore 私钥/密钥材料**不可跨设备迁移**，密文被备份到新机后无法解密 → 换机后授权直接不可验证，比"不备份"更糟；
- 私密内容不会污染历史（`PRD:95` 的零留痕拦截仍生效），所以本项与 AC-02 **不冲突**，无需为此破例。

因此落点是一份细化的排除规则（`dataExtractionRules` / 旧版 `fullBackupContent`）：

1. 备份白名单内只放**观看历史 + 续播断点 + 排版/主题偏好**；
2. **显式排除**凭证域（JWT 及其安全存储文件）与公开缓存域（目录快照、海报，可重建，备份纯属浪费配额）；
3. 一键清空的语义范围限定为"历史与断点"，不得顺带清掉凭证与偏好，与 AC-18"清缓存不清凭证/续播"的既有口径保持同一套存储域划分；
4. 这一项与 R-14 一起构成"端侧存储契约"的必需内容：**必须先写存储域划分（凭证域 / 续播域 / 缓存域 / 禁止落盘域），再写备份规则**，顺序不能反。
